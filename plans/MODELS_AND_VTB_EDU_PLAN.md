# Модели Cloud.ru и Yandex AI Studio и вход через VTB Edu

План от 24.11.2026. Выпуск состоит из двух независимых частей. Первая расширяет рабочий каталог моделей. Вторая добавляет вход VTB Edu через Yandex Identity Hub рядом с существующим входом через Яндекс ID.

## Первый этап в репозитории

Скрипт [check_model_candidate.py](../scripts/check_model_candidate.py) проверяет одну модель через адаптер Gosboard: обычный ответ, поток, два варианта маршрутизации и ответ с проверяемой ссылкой на синтетический документ. В тестовой среде с настроенным backend можно запустить его из корня репозитория.

```bash
docker compose exec -T backend python - deepseek-v4.1-flash --allow-paid < scripts/check_model_candidate.py
```

Для Cloud.ru подставьте `cloudru/ai-sage/GigaChat3-10B-A1.8B`, `cloudru/ai-sage/GigaChat3.5-432B-A28B` или `cloudru/GigaChat/GigaChat-3-Pro`. Один запуск отправляет до пяти платных запросов вне лимитов Gosboard и прекращается при первой ошибке. Скрипт не открывает SQLite. Проверки сохранения чатов, обработки отказов и учёта расходов выполняются отдельно через приложение в тестовом пространстве.

Для проверки Cloud.ru заполните `CLOUDRU_API_KEY` в существующем игнорируемом `.env` или в `/etc/aitalks/production.env` на сервере. Для DeepSeek используются `YANDEX_CLOUD_FOLDER_ID` и `YANDEX_AI_API_KEY`. В [шаблоне окружения](../.env.example) также подготовлены поля для клиента, секрета, OpenID Configuration и issuer VTB Edu. Включайте `VTB_EDU_ENABLED=true` после настройки OIDC-приложения. Для обмена кода разрешите `client_secret_post` в Identity Hub.

### Проверка VTB Edu

Команда `PYTHONPATH=backend python scripts/check_vtb_edu_discovery.py` использует `VTB_EDU_DISCOVERY_URL` и `VTB_EDU_ISSUER` из окружения процесса. Данные VTB Edu прошли проверку: issuer совпал, адреса принадлежат Identity Hub, метаданные объявляют RS256. Проверка выполняет только запрос публичной конфигурации.

Домены двух способов входа разделены по решению владельца. VTB Edu принимает только точный домен `vtb.education`. Этого достаточно для использования существующей схемы допуска и членства. Регистрация VTB Edu использует идентификатор на основе issuer и sub и статус «Ожидает допуска». Вход требует подтверждённого корпоративного email. Если Identity Hub не возвращает `email_verified`, сервер может подтвердить конкретный адрес по заранее сверенной в каталоге организации паре email и `sub` из `VTB_EDU_PINNED_SUBJECTS`. Этот вариант также требует действительного ID-токена для данного приложения и совпадения `sub` в UserInfo. Явный отказ в подтверждении email отклоняется. Если администратор заранее создал и включил запись для корпоративного адреса, после подтверждения личности используется заданная роль. При первом входе без такой записи создаётся заявка. Для допуска пилотного аккаунта ещё нужно подтвердить доверенный атрибут корпоративного email.

## Каталог моделей

Адаптер Cloud.ru и маршрутизация по префиксу `cloudru/` уже реализованы. В `config/app.json` есть начальные записи для GigaChat 3 и DeepSeek V4.1 Flash. На действующей установке рабочий каталог хранится в SQLite. Новые позиции следует внести в очередную ревизию через существующую административную конфигурацию после проверок.

| Провайдер | Кандидаты | Условие включения |
| --- | --- | --- |
| Cloud.ru Foundation Models | `ai-sage/GigaChat3-10B-A1.8B`, `ai-sage/GigaChat3.5-432B-A28B` | Модели доступны с ключом проекта и проходят проверку потокового ответа и структурированного вывода для маршрутизации и RAG. |
| Yandex AI Studio | DeepSeek V4.1 Flash с URI `gpt://<folder_id>/deepseek-v4.1-flash` | Основной кандидат на роль резервного варианта. Другие модели семейства добавляются, когда каталог конкретного проекта подтверждает поддержку текстового API и они проходят те же проверки. |

[Каталог Cloud.ru Foundation Models](https://cloud.ru/docs/foundation-models/ug/topics/overview__available__models) · [Каталог Yandex AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models)

1. Получить от владельца ключ сервисного аккаунта Cloud.ru с доступом к Foundation Models. Хранить его в защищённом окружении сервера как `CLOUDRU_API_KEY`. Для Yandex сначала проверить доступ с существующим ключом и в настроенном каталоге. Сверить доступные ID, квоты и тарифы по обоим проектам. [Настройка ключа Cloud.ru](https://cloud.ru/docs/foundation-models/ug/topics/quickstart) · [Получение списка моделей Yandex AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/models/get)
2. Для каждого кандидата проверить на синтетических данных обычный ответ, потоковый ответ, выбор источников при разных формулировках и ответ с проверяемыми цитатами. Отдельно проверить отказ провайдера, обрыв потока и учёт расходов. Параметры рассуждений включать после проверки для конкретной модели.
3. Зарегистрировать прошедшие проверку модели в рабочем каталоге. Оставить текущую модель по умолчанию и сохранённые профили. Подготовить тестовое пространство с DeepSeek. Предлагаемый первый выпуск использует его как резерв, который администратор или управляющий выбирает в настройках пространства для новых разговоров.
4. Автоматическое переключение, если оно потребуется, согласовать отдельно. DeepSeek в Yandex AI Studio может помочь при сбое отдельной модели, но сбой общего API, ключа или квоты может затронуть обе модели. Пробный запуск GigaChat проводить в отдельном пространстве. Ограничение на его использование в сценарии 27 ноября сохраняется до решения организаторов. [Согласования по мероприятию](DEVELOPMENT_PLAN.md)

## Вход через VTB Edu

### Настройка приложения владельцем

1. В [Cloud Center → Приложения](https://center.yandex.cloud/organization/apps) создать OIDC-приложение типа **Web Application** в нужной организации. Предлагаемый URL возврата для регистрации — `https://aitalks.tech/api/auth/vtb-edu/callback`.
2. Оставить PKCE и включить области доступа `openid email profile`. В разделе пользователей и групп приложения назначить только нужных участников VTB Edu. Предоставить клиентский ID, URL **OpenID Configuration** и клиентский секрет. Значения секретов передать по защищённому каналу. [Создание приложения](https://yandex.cloud/ru/docs/organization/operations/applications/oidc-create) · [Доступ к OIDC-приложению](https://yandex.cloud/ru/docs/organization/concepts/applications/oidc)

### Реализация в Gosboard

1. Сохранить кнопку **Войти с Яндекс ID** и её текущий маршрут. Добавить **Войти с VTB Edu** сразу под ней. Публиковать новую кнопку только при включённой и настроенной интеграции. Добавить отдельные маршруты `/api/auth/vtb-edu` и `/api/auth/vtb-edu/callback`.
2. Использовать `https://auth.yandex.cloud` для корпоративного входа. Взять адреса авторизации, обмена кода и ключей проверки подписи из OpenID Configuration созданного приложения. Закрепить ожидаемый issuer и проверить его точное совпадение с metadata и токеном. Использовать отдельное одноразовое состояние входа, PKCE S256 и nonce. На сервере проверить подпись ID-токена по JWKS, аудиторию, срок действия и nonce. Брать email из доверенных данных провайдера. Если нужен UserInfo, сверить его `sub` с ID-токеном. Принимать только точный нормализованный домен `vtb.education`. На пилоте подтвердить, какой атрибут организации удостоверяет принадлежность email, и отклонять вход при отсутствии необходимых данных. [OIDC в Yandex Identity Hub](https://yandex.cloud/ru/docs/organization/concepts/applications/oidc)
3. Идентифицировать VTB Edu по паре `issuer + sub` в отдельном пространстве идентификаторов. Сохранить существующие идентификаторы `yandex:…`, чаты и назначения. Новые пользователи VTB Edu добавляются отдельными записями в общий список аккаунтов со статусом «Ожидает допуска». Учётные записи двух способов входа считаются раздельными. Автоматического связывания по email нет. Для VTB Edu применяется требование домена `vtb.education`, а вход через Яндекс ID сохраняет действующие правила. Корпоративный вход подтверждает личность. Допуск в приложение остаётся отдельным решением администратора.
4. Добавить отображение способа входа в административном списке, чтобы различать заявки. В журнале фиксировать результат и тип входа без токенов и секретов. Хранить клиентский секрет только на сервере. Флаг отключения VTB Edu должен скрывать кнопку и закрывать новые корпоративные входы. Предусмотреть отдельное завершение уже выданных сессий VTB Edu при отключении по соображениям безопасности.

## Приёмка и выпуск

- **Модели.** Каждый добавленный ID доступен в рабочем каталоге, проходит проверку обычного и потокового ответа, корректно выбирает поиск или прямой ответ и сохраняет проверенные цитаты. Лимиты расходов и текущие чаты сохраняются. Проверки с реальными ключами проводят небольшими сериями на тестовых материалах.
- **Вход.** Проверить обе кнопки, первый и повторный вход VTB Edu, допуск нового пользователя и назначение пространства. Проверить отказы для другого домена, отсутствующих атрибутов, повторного callback и подмены issuer, аудитории или nonce. Прогнать регрессию входа Яндекс ID и доступа к существующим чатам.
- **Развёртывание.** Сначала подготовить резервную копию и проверить восстановление с изменённой схемой на изолированной среде. Модели и VTB Edu включать отдельно после своих проверок. Для отката моделей использовать ревизию каталога и блокировку конкретной модели с учётом чатов, где она уже выбрана. Для остановки новых корпоративных входов отключить флаг VTB Edu. Обновить руководства по ролям при выпуске.
